# Funding-flow loss checks across approved folds

All four served populations use `funding_population.py`: USD total/basis/currency, research scope/true, organisation awards/matches/memberships, and country/region awards and country memberships. The existing fuse thresholds are unchanged.

Published rows are mapped through the checked `resolve_candidate`. Missing/GONE rows retain their original IDs in the baseline: a lost source or missing candidate cannot erase its own expected count. Scalar fields use the survivor's prior row (falling back deterministically when the survivor was not previously public). Organisation memberships union and deduplicate the entire served object at the resolved ID; overlapping roles remain distinct. Geography deduplicates locations and applies basis priority. Served regions in the current producers are funder-reported. Neither source-row counts nor source receipts use this adjustment.

For NIH `amount=null`, expected USD counts exclude only `nih_choice` survivors, matching the projection in `nih_fold.project` before conversion. The baseline does not infer nulling from tonight's amount values. `sum`/`elected` do not receive the nulling exemption. Pending held losers remain independently counted unless the checked resolver actually redirects them.

On the first publication, yesterday's table does not have these fields. A scalar bootstrap cannot identify which awards a fold will remove. A first-release fold therefore requires the optional `funding_flows_baseline` extra input: a frozen full pre-fold candidate built on the same input versions with the reviewed funding-flow code. The runtime pins it like every other extra input. Each pre-resolution quantity must first pass its existing bootstrap/last-successful-count fuse; the baseline must include previous IDs involved in redirects. The post-resolution quantity is then used for the served gate. Missing baseline data stops the run; no raised fuse or global waiver is substituted.

Before the first combined publication: build/check the pre-fold candidate on frozen inputs, retain its input-version manifest and full-field acceptance, configure that artifact as `funding_flows_baseline`, then run the fold-inclusive `stop_before_apply` check. Stage a production-accessible frozen baseline only with explicit authorization. Later nights use `previous_api_v` whenever it contains the field, regardless of whether an old bootstrap artifact remains configured.

Counts `funding_before_*` (bootstrap input) and `funding_expected_*` (after approved resolution and policy) are written into nightly details alongside the actual counts. Raw recipient feed/kind counts, classification counts, raw/GtR source receipts, endpoint loss fuses, and rate input shape/nonempty gates remain independent. A change in research policy still requires its own review; a fold adjustment is not a policy waiver.
